# VMTech AI outcomes

- [x] **General assistant experience** — VMTech AI provides skill choices for automation drafts, code debugging, teaching/explanations, learning plans, project/business plans, and general questions. It presents plans and code as drafts; it does not claim to execute workflows or run code.
- [x] **Responsive assistant UI** — Keep the skill navigation, prompt examples, chat composer, loading/error/retry states, copy control, new-chat behavior, mobile layout, brand, and route manifest. Desktop/mobile layouts were reviewed in the design pass; the local-model readiness indicator and setup notice now reflect the runtime.
- [x] **Local inference and self-hosting** — Provide local Ollama with Qwen 3.5, a Compose app/runtime, safe loopback defaults, provider endpoint restrictions, and CPU/GPU setup documentation. A real Qwen 3.5 4B answer was tested through the app; Compose itself could not be run because Docker is unavailable in this sandbox.
- [x] **Faster end-to-end responses** — Show assistant output as it streams token-by-token instead of waiting for full completion; abort generation when the conversation is reset or the client disconnects; keep conversation context under 18,000 characters and bound output. Keep the local model warm for 30 minutes by default to reduce repeated cold starts, configurable for lower-RAM machines. With the same short coding question and same 100-character answer, a cold Qwen 3.5 4B request took 10.421 seconds to first token and 11.415 seconds total; repeating it warm took 0.162 seconds to first token and 1.323 seconds total. An earlier non-streaming release recorded a 12.56-second first response. These are single-run sandbox measurements, not a general hardware guarantee. Streaming improves time-to-first-visible-content; warm retention reduces repeat load time but uses RAM.
- [x] **More useful coding workspace** — Provide explicit Debug, Review, Write tests, and Explain code guidance. Let users attach small text/source files (maximum 16,000 characters), read the file in the browser without creating a stored upload, and send it only to the active provider. Keep prompt plus recent conversation within 18,000 characters; advise users to review generated code and never run it automatically.
- [x] **Structured automation drafts** — Make workflow drafts include goal, trigger, inputs/permissions, numbered steps, branches, errors/retries, tests, rollback/deactivation, and external connections required. Allow a Markdown draft download. Do not execute, schedule, message, or connect external accounts without user-selected integrations and separate authorization.
- [x] **Optional user-supplied API provider** — Keep local Ollama the default. Add an OpenAI-compatible provider configuration for base URL, model, and user API key, usable only after explicit selection. In hosted Preview, disable key entry. In the loopback-only self-hosted app, accept the key in Settings and keep it server-side in memory only; never echo, log, return, persist in browser storage, or write it to disk. Clear it on server restart; use HTTPS for public providers; require explicit trust for private endpoints; reject redirects and cross-origin or origin-less settings mutations; never silently fall back. Report provider state without exposing the credential. A real external provider was not called or configured during testing.
- [x] **Complete theme switch** — Provide Light, Dark, and System modes, apply each throughout the VMTech workspace, and persist the theme choice in browser local storage.
- [x] **No unnecessary external UI requests** — Remove remote-font dependencies and live Manus/OAuth integrations from application startup and browser bootstrap. A model-weight download during installation is allowed; the local provider uses local Ollama.
- [x] **Lee local model profiles** — Add selectable **Lee 1.0** for fast questions and answers, **Lee 2.0 Lite** for automations and tasks, and **Lee 2.0 Pro** for coding and complex tasks. Recommend Lite for automation/planning skills, Pro for coding, and Lee 1.0 for general, teaching, and learning skills; let the user choose a different profile. Treat these as VMTech profile names, not new trained model weights. Map them by default to configurable Ollama tags `qwen3.5:4b`, `qwen3.5:9b`, and `qwen3.5:27b`, respectively. Show the backing tag and the selected profile’s installed/download-needed status; provide the direct Ollama and Compose pull commands for a missing tag and do not silently fall back to another profile. Keep Lee profiles local-Ollama-only; when a remote provider is selected, identify it as the active provider instead. Explain that Lee 2.0 Pro's 27B default is a large 17–20 GB model download that needs substantial host memory, and allow operators to map each profile to a different local Ollama tag. Verified the profile/status paths for all three, a real Lee 1.0 Qwen 4B streamed answer, and a real Lee 2.0 Lite Qwen 9B automation answer; Lee 2.0 Pro remains an optional tag not downloaded in this sandbox.

Verification for the Lee profile update: `pnpm check` passed; all 22 tests passed; `pnpm build`, Prettier, and `git diff --check` passed. Live status correctly reported the installed Lee 1.0 and Lite tags and the uninstalled Pro tag; both 4B and 9B returned streamed answers. A CPU-only Lite automation run took about 76 seconds end-to-end, so response time depends on host hardware. Docker Compose could not be executed because Docker is not installed in the sandbox.
